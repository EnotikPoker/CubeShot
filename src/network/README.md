# Сеть CubeShot 0.14.0

`cubeshot_network` — статическая библиотека без SDL. GameNetworkingSockets
закреплена на v1.6.0 (`2cb93a06350bb065db53abdb0d87cf297e0bfd34`); ICE/P2P,
Steam и SDR не используются. Соединения напрямую по IPv4 поверх UDP. Сервер явно привязывается
к `0.0.0.0:port`, чтобы GNS не обходила конфликт порта через fallback IPv6/IPv4.
Сериализация — Protobuf, `protocol.proto`, номер протокола **6**.
Изменение несовместимого формата или арены требует изменения номера протокола.

## Разделение ответственности

- `Server.h/.cpp` и `Client.h/.cpp` — отдельные сессии с публичными
  интерфейсами без заголовков GNS и Protobuf. `Session.h/.cpp` удалены.
- `detail/GnsRuntime` владеет временем жизни GNS и реестром callbacks,
  общими для всех сессий одного потока.
- `SnapshotInterpolation` хранит историю снимков и интерполирует чужие
  позиции на 33 мс назад, не смешивая фазы/раунды. `Client` добавляет prediction.
- `Address` проверяет IPv4:порт независимо от сессий; `NetworkSimulation`
  включает имитацию задержек и потерь только для тестов.

- `Protocol` создаёт конверты, сериализует снимки, проверяет версию,
  размер, конечность чисел, пределы здоровья/счёта, количество и уникальность ID.
- `Server` назначает ID по соединению, принимает управление, исполняет
  авторитетный `Match`, публикует состояние и обрабатывает разрывы.
- `Client` отправляет управление и дискретные действия, отбрасывает старые
  снимки по tick, предсказывает своего персонажа и интерполирует чужие
  сущности с задержкой 33 мс по стабильным ID.
- `Discovery` отдельно от игрового транспорта: UDP IPv4 broadcast на 27016,
  запрос `CSQ1` и Protobuf с nonce, unicast-ответ `CSR1`. Опрос раз в 2 с,
  время жизни комнаты 6 с. Используются broadcast-адреса активных интерфейсов,
  общий broadcast и loopback. Ручной IP работает без discovery.

Все методы сессии вызываются из одного потока; фоновый UDP-поток управляется
самой GameNetworkingSockets. RAII обеспечивает закрытие слушателей,
соединений, poll group и завершение библиотеки после последней сессии.

## Протокол и частоты

| Сообщение | Доставка и смысл |
| --- | --- |
| Hello → Welcome | Надёжно; версия, ник, owner/reservation token, назначение ID сервером |
| Control | Ненадёжно, 60 Гц; round и до8 InputCommand (sequence, движение, прицел) |
| Action | Надёжно, по событию; sequence + round, один прыжок или выстрел; направление в момент нажатия |
| Ready, Leave | Надёжно; готовность/реванш и добровольный выход |
| Snapshot | Полный снимок 60 Гц ненадёжно, при смене фаз дополнительно надёжно; tick + round + фаза + счёт + слоты + сущности |

Сервер обновляет Match с фиксированным шагом **1/120 с**. Не принимает
позиции, здоровье, урон, победу или PlayerId от клиента. ID определяется
соединением. Повторные/старые Action не выполняются; пакеты другого раунда
не действуют. Control с меньшим sequence отбрасывается. Направление отдельного
выстрела сохраняется независимо от последующих Control. Частота оружия
ограничена сервером, удержание ЛКМ не вызывает автоматический огонь.

Максимальный игровой пакет 64 КиБ; snapshot не более двух игроков и 64 пуль,
максимум одновременно существующих пуль штатного пистолета меньше этого.
Discovery не более 512 байт. Некорректное сообщение закрывает соединение.
Третий участник и вход в начатый матч отклоняются. Нового гостя можно принять
в лобби после выхода предыдущего. Готовность и счёт при этом сброшены.

В автоматической комнате сервер резервирует ID 1 владельцу через случайный
owner token; гость может занять ID 2 только после входа владельца. Токен
служит защите назначения слотов при старте, не системой аккаунтов.
Самостоятельный сервер без токена назначает ID 1 и 2 первым участникам.

При неполучении Control **250 мс** горизонтальное движение прекращается;
гравитация и серверные пули продолжаются. При отсутствии игровых сообщений
**5 с** участник отключается, матч отменяется без очков. Начальное подключение
также ограничено 5 с. Если auto-server не дождался хозяина за 10 с, он завершится;
после потери уже подключённого хозяина завершится сразу.

Снимок содержит input_ack/action_ack обоих слотов, ники и стабильные BulletId, сохраняемые при сбросах раундов.
Интерполяция не соединяет разные фазы/раунды и не создаёт удалённые пули.
Предсказание добавлено в0.7.0 и используется вLAN/интернете. Rollback, lag
compensation и клиентского определения попаданий нет.

## Процесс сервера

`HostProcess` клиента запускает `cubeshot_server` через SDL3. Это отдельный
процесс, поэтому личное меню или зависший клиент не замораживает симуляцию.
При выходе из комнаты клиент закрывает соединение, останавливает и ожидает
процесс; при необходимости применяется принудительное завершение.
`cubeshot_server` должен лежать рядом с клиентом, вместе с runtime-библиотеками.

Сборка сервера возможна с `CUBESHOT_BUILD_CLIENT=OFF` без поиска SDL3.
Правила дуэли, арена и HP описаны в `src/game/Match` и `src/game/README.md`.

## Предсказание 0.7.0

Клиент симулирует своего Player через общую физику с шагом 120 Гц.
Control содержит до восьми последних InputCommand; пакет отправляется 60 Гц.
Сервер хранит максимум 240 команд, исполняет максимум одну за тик, при пропуске
ждёт два тика и продолжает со следующей доступной. Это не ускоряет серверное
время. После 250 мс без ввода движение останавливается, через 5 с — disconnect.
Action доставляется надёжно, привязан к input_sequence и выполняется один раз.
Snapshot содержит input_ack/action_ack для обоих слотов; Bullet содержит
shot_sequence для удаления предварительного эффекта. Подтверждение действия
означает обработку, а не гарантированное попадание или принятие по кулдауну.
Prediction повторяет неподтверждённый ввод, ограничивает историю двумя секундами,
сбрасывается на границах фаз/раундов и при смерти. Поправки до 96 пикселей
сглаживаются только в рендерере. Предварительные пули сталкиваются лишь с
геометрией, не меняют HP и исчезают по подтверждению действия. Чужие сущности
интерполируются с задержкой 33 мс; rollback/lag compensation пока отсутствуют.
Транспортный тест добавляет 75 мс на отправку каждой стороны, до 30 мс jitter
и 5% потерь: это базовый RTT 150 мс плюс jitter и восстановление потерь.

## Интернет0.8.0

`Directory` — фоновый HTTPS-клиент списка и бронирований. Он не вызывает GNS
из рабочих потоков. Отмена обрабатывает также поздний ответ с токеном.
`cubeshot_online_server` / `online::Service` содержит пул `Server`, каталог
и очередь запросов от двух HTTP workers. Все изменения арен и бронирований
выполняет один поток симуляции. Клиент не может выбрать PlayerId: он назначен
арене/слоту в одноразовом256-битном токене, TTL10с. Приёмник `AdmitPlayer`
проверяет токен/ник; LAN использует прежний owner-token либо свободные слоты.
Интернет-сервер не зависит от ухода первого игрока и не запускает discovery.
На смене соединения/раунда/фазы очищаются prediction и ожидающие действия.
При переполнении240команд предсказание ждёт следующего снимка и восстанавливает
номер команды из серверного подтверждения.
API, ограничения и запуск: [ONLINE.md](../../docs/ONLINE.md).

## Координация клиента и сервиса

`client::ConnectionController` владеет `Client`, `Discovery`, `Directory`
и дочерним `HostProcess`. Он обрабатывает подключение, отмену, выход, готовность
и сетевые переходы меню. `Application` передаёт ввод в текущую сессию и
отрисовывает снимки; нейтрализация ввода и локальная тестовая World остаются там.

`online::Service` координирует три модуля:

- `ArenaPool` владеет игровыми серверами и вызывает их poll/step.
- `Reservations` хранит TTL, занятость, повторы, отмену и одноразовый допуск;
  не включает HTTP/JSON и работает только в потоке симуляции.
- `HttpApi` принимает HTTP, ограничивает запросы, проверяет и сериализует JSON.
  Два workers ставят запросы в очередь; poll обрабатывает её в потоке симуляции.

Порядок завершения: HTTP останавливается до удаления бронирований и арен.
Протокол 3, частоты, порты, игровые правила и видимые пользователю переходы
при разделении модулей не менялись.

## Настройки и ник 0.9.0

Ник редактируется через «Настройки → Игрок», а не в интернет-меню.
ConnectionController фиксирует имя при старте бронирования, сохраняет его
для позднего ответа и handshake. Изменение профиля в текущем матче влияет
только на следующее подключение, протокол 3 не менялся.
Settings-экран сохраняется при новых снимках/сменах фаз, но сеть продолжает
poll/control с нейтральным вводом. После закрытия настроек Menu выбирает
актуальное лобби/результат/паузу. При потере соединения обычный сетевой
переход закрывает настройки с отменой неподтверждённого режима окна.


## Карты и события 0.10.0

Протокол 4 передаёт MapId, голоса, ревизию выбора и последовательность снимков.
Геометрия общая для клиента и сервера; неизвестные MapId отклоняются.
LAN позволяет выбирать карту слоту 1; онлайн требует голосов обоих до Ready.
Смена выбора сбрасывает готовность. Устаревшие команды не меняют состояние;
клиент повторяет неподтверждённый выбор после получения свежей ревизии.
Карта фиксируется на матч; реванш повторяет её, ChangeMap открывает новое
голосование после результата. Disconnect очищает голоса и готовность.

Shot/Hit/Death/SurfaceImpact доставляются надёжными событиями, отдельно от
снимков. Клиент исключает повторы и сопоставляет свой предварительный выстрел
по shot_sequence. Эффекты не участвуют в расчёте урона. При смене карты/раунда
сбрасываются предсказание, интерполяция и эффекты. Контакты тел используют
BodyPhysics как на сервере, так и при повторе команд предсказания.


## Бой и рулетка 0.13.0

Протокол 5 несовместим с 4. Player передаёт WeaponKind, cooldown,
charging/preparation и счётчик залпов. Bullet — оружие, урон, гравитацию и volley.
InputCommand.fire_held независим от надёжного дискретного клика; потеря ввода
250 мс сбрасывает удержание. Автоогонь и подготовка снайпера подчиняются общей
физике 120 Гц: транспорт не может повысить темп огня. Prediction использует те же
scatterShot и таймеры; подтверждение volley не повторяет отдачу или дробь.

Snapshot включает два трупа и до 128 PhysicsPiece с устойчивыми ID, маской ячеек
и целостностью. Позиции и углы интерполируются, разрушение решает сервер.
Снимок допускает до 256 пуль, общий лимит пакета 64 КиБ сохранён. Клиент не
присылает останки, урон или исход рулетки.

После четырёх секунд RoundEnd сервер открывает Armory. WeaponChoice проверяется
по раунду, ревизии и статусу Pending. Повторный бросок невозможен. Результат
равномерный 0–6, включая текущее оружие; вращение — 2,4 с, показ результата —
0,8 с. Оба готовы — Countdown на три секунды. В RoundEnd победитель продолжает
управлять, HP и счёт зафиксированы. Последний раунд через четыре секунды ведёт
в Finished. Ready из лобби не заменяет WeaponChoice.

## Арсенал 0.14.0, протокол 6

Снимки передают до 48 очагов огня, горение/источник поджигания, маску сколов,
разгон/температуру/перегрев минигана, возраст/возврат/маску попаданий бумеранга.
ID первых семи видов сохранены, каталог расширен до четырнадцати.
Новый Explosion даёт визуальный взрыв, сам урон рассчитывает World сервера.
Валидация включает пределы новых таймеров, масок, размеров и конечность чисел;
клиент не присылает урон, горение или результат броска.

## Визуальное обновление 0.15.0, протокол 7

Player.surface передаёт до шести EdgeChip, revision и charred вместо маски
старых клеток. Piece передаёт polygon outline, skinOffset, integrity, revision,
charred; hull восстанавливается на приёме. Corpse содержит причину смерти
вместо клеток. Снимки отклоняют неверные, пересекающиеся и слишком большие
контуры, пересекающиеся сколы и неконечные координаты. Пустой контур разрешён
только для уничтоженного основного трупа. Старые номера protobuf зарезервированы.
События содержат body-local hit, surfaceRevision и volleyDamage: эффекты
привязываются к текущей интерполированной позе, не к устаревшей мировой точке.
Сервер остаётся источником урона и физики; клиент не выбирает форму разрушения.
