# Приёмка текущей версии 0.14.0

Клиент и сервер должны быть одной версии: протокол 6 несовместим с протоколом 5.
В дополнение к базовому LAN-сценарию ниже проверить на обоих компьютерах:

1. После смерти четыре секунды сохраняется управление победителем. Оба участника
   видят одинаковый труп, толчки, попадания и отлетающие части; результат не меняется.
2. «Продолжить» сохраняет ствол, «Сменить оружие» вращает колесо только один раз.
   Одновременный выбор и повторный клик не меняют исход. Оба готовы — отсчёт 3 с.
3. Автомат и SMG стреляют при удержании. Отпускание, меню и потеря ввода останавливают
   огонь. Снайпер готовится 0,3 с: индикатор виден, раннее отпускание отменяет выстрел.
4. Дробь, раны и трупы соответствуют серверу. Новый раунд очищает останки и
   восстанавливает HP, оружие сохраняется; реванш снова даёт пистолеты.

5. Проверьте перегрев минигана у обоих клиентов; РПГ задевает стрелка и наносит
   меньше урона у края взрыва; огонь поджигает обоих и затухает. Бумеранг виден
   в обоих направлениях, ближний удар не проходит через стены.

Матрица и ограничения этой ветки указаны в tests/README.md. Нативную Windows
проверяет CI; проверки между компьютерами ниже нельзя заменить двумя клиентами
на одной машине.

## Историческая приёмка LAN 0.6.1

## Проверено в текущей Linux-среде

- Сборка клиента/сервера Debug; 8 проверок CTest.
- Отдельная сборка сервера Release с `CUBESHOT_BUILD_CLIENT=OFF`; 5 проверок CTest.
- Правила: оба Ready, 3 с отсчёта, пять побед, смена сторон, здоровье/пули,
  ничья, реванш, выход в лобби без присуждения победы.
- Protobuf: roundtrip, несовместимая версия, неправильные ID/значения/размеры.
- Реальный UDP: два клиента, третий отклонён, проверка owner slot,
  остановка устаревшего ввода 250 мс, таймаут 5 с, новый гость, выход хозяина.
- Доставка пяти выстрелов и одинаковый счёт обоих клиентов при имитации
  **100 мс задержки отправки и 5% потери исходящих пакетов** в GameNetworkingSockets.
- Discovery: обнаружение, статус занятой комнаты, исчезновение спустя 6 с.
- SDL-процесс: старт, подключение хозяина, остановка/ожидание, освобождение
  порта и ошибка при занятом порте.
- Отрисовка LAN-экранов через SDL software renderer; изображения интерфейса.
- Два независимых SDL-клиента в X11 на одном Linux-компьютере: создание
  комнаты, список, вход гостя, готовность, арена, Esc, выход хозяина и
  возврат гостя в список с сообщением (проверено по снимкам окон).

В CI 0.6.0 Windows успешно собирает программы и проходит 7/8 проверок:
`host_process` обнаружил, что второй сервер запускался на том же порту через
смену IPv6/IPv4. В 0.6.1 сервер явно слушает IPv4; этот тест сохранён.
В Linux CI конфигурация зависимостей выявила отсутствие `autoconf-archive`,
затем `libltdl-dev` для `libxcrypt`. В подготовку runner добавлены полный
набор autotools и предварительная проверка макросов из закреплённого vcpkg.
Windows CI 0.6.1 успешно прошёл во всех четырёх прогонах (PR/push веток/тега),
включая `host_process`. Дополнение Linux CI требует повторного запуска.
При новых сбоях workflow сохраняет CMake/vcpkg/CTest логи в артефакт `CI-logs-*`.

Локально 0.6.1 проходит все 8 тестов, включая занятый нативным IPv4 сокетом
порт и попытку двух серверов слушать один порт. Тесты на одном компьютере
не подтверждают broadcast и сетевой экран между двумя реальными машинами.

## Проверка на двух компьютерах

Нужно выполнить **Linux↔Linux**, **Windows↔Windows**, **Linux↔Windows**.
Для смешанной пары поменять, какая ОС создаёт комнату.

1. Разместить клиент, сервер и runtime-библиотеки одной версии рядом.
   Подключить компьютеры к одной сети, разрешить входящий UDP 27015/27016.
2. Создать комнату. Найти её на другом ПК; проверить адрес и `1/2`.
   Убедиться, что третьему клиенту отказывают. Повторить вход по IPv4:порт.
3. Один Ready не запускает игру. Оба Ready запускают отсчёт 3 с.
   Проверить два игрока, симметричную арену и локальный синий цвет у каждого.
4. Одновременно идти, прыгать, целиться и стрелять. Пять попаданий по 20
   приводят к смерти, клик создаёт один выстрел, удержание не стреляет.
   Стены закрывают игрока, пули видны обоим, собственные пули не наносят урон.
5. Проверить счёт, четыре секунды после смерти, выбор оружия и новый отсчёт 3 с,
   полное HP, отсутствие старых пуль/останков и чередование точек появления. Довести до 5 побед и согласовать реванш.
6. В LAN открыть Esc: свой ввод прекращается, второй игрок и серверные пули
   продолжают двигаться; находящийся в меню игрок может получить урон.
   R ничего не сбрасывает. «Тест» сохраняет настоящую паузу и перезапуск R.
7. Гость выходит в лобби и во время раунда: хозяин остаётся в лобби,
   счёт/Ready сброшены, победа никому не засчитана. Присоединить нового гостя.
8. Хозяин выходит: гость видит сообщение и возвращается к комнатам,
   сервер завершён. Снова создать комнату на том же порту.
9. Отключить сеть/закрыть процесс клиента: через 5 с матч отменяется.
   Остановка лишь потока ввода прекращает движение уже через 250 мс.
10. Запретить discovery UDP 27016: автоматический список не находится,
    прямой IPv4 на 27015 продолжает работать. Запретить 27015: видна ошибка
    подключения, приложение остаётся доступным. Повторить с занятым портом.

## Автоматические проверки

```bash
ctest --test-dir build --output-on-failure
# На Windows:
ctest --test-dir build -C Release --output-on-failure
```

В тестах сетевой сессии порты 29720–29722, discovery 29716/29715,
дочернего сервера 27015. Новый `connection` использует UDP29840/29841/29850. Во время `host_process` порт 27015 должен быть свободен.
Проверки одной и той же сборки не следует запускать параллельно отдельными
процессами CTest из-за этих фиксированных тестовых портов.

Чтобы сохранить изображения новых экранов, установите
`CUBESHOT_CAPTURE_DIR` в путь каталога и запустите `cubeshot_menu_tests`.
Результат — BMP, никаких внешних шрифтов и графического окна не требуется.
